# Provider-Neutral Python Project Structure

**Status:** AWS Syndicate project standard  
**Audience:** Human contributors, coding agents, IDE assistants, and CI
automation  
**Supported Python:** 3.14

This document describes the repository structure generated by the
`python-standard` project template. It adapts a provider-neutral Python
engineering standard to an AWS Syndicate application. The generated project
remains an AWS project first: deployment configuration, Lambda layout, and AWS
safety rules are part of the standard.

## Source of truth

The responsibilities of the main files are intentionally separate:

| File or directory  | Responsibility                                                   |
|--------------------|------------------------------------------------------------------|
| `AGENTS.md`        | Short, canonical instructions for contributors and coding agents |
| `README.md`        | Human onboarding, usage, and deployment guidance                 |
| `CHANGELOG.md`     | Project history                                                  |
| `pyproject.toml`   | Python metadata, dependencies, and test configuration            |
| `uv.lock`          | Generated dependency resolution                                  |
| `docs/`            | Detailed architecture and engineering standards                  |
| `lambdas/`         | Lambda handlers and their deployment source                      |
| `commons/`         | Shared application code                                          |
| `tests/`           | Unit, integration, and end-to-end test layers                    |
| `skills/`          | Optional, portable agent workflows                               |

`AGENTS.md` is deliberately concise. This document contains the detailed
standard and should be linked from project documentation rather than duplicated
in every tool-specific adapter.

The implementation of the scaffold is bundled in
`syndicate/core/generators/python_standard.py`. Changes to this standard and
the generator must be reviewed together; the CLI does not read files from a
developer's local machine at runtime.

## Generating a project

The standard is opt-in so existing generated projects remain compatible:

```shell
syndicate generate project \
    --name sample-app \
    --path C:\work \
    --template python-standard
```

The available templates are:

| Template          | Behavior                                                              |
|-------------------|-----------------------------------------------------------------------|
| `legacy`          | Existing AWS Syndicate project scaffold; default                      |
| `python-standard` | Python 3.14 scaffold with `uv`, agent guidance, docs, and test layers |

The generator creates files only. It does not deploy resources, access AWS, or
create a virtual environment. Run `uv lock` or `uv sync` in the generated
project when you are ready to resolve dependencies.

## Generated layout

```text
sample-app/
├── AGENTS.md
├── CHANGELOG.md
├── README.md
├── deployment_resources.json
├── pyproject.toml
├── uv.lock                         # generated locally by uv
├── .python-version
├── .env.example
├── .gitignore
├── venv.md
├── commons/
├── lambdas/
├── docs/
│   └── architecture.md
├── skills/
│   └── verify-project/
│       └── SKILL.md
└── tests/
    ├── unit/
    │   └── test_scaffold.py
    ├── integration/
    │   └── README.md
    └── e2e/
        └── README.md
```

The template does not create `CLAUDE.md`, a root `SKILLS.md`, or a real `.env`
file. Tool-specific adapters and local secret files are optional and should be
added only when the project actually uses them.

## Environment and dependencies

The generated project targets Python 3.14 and uses `uv`:

```shell
uv sync
uv run pytest tests/unit
uv run pytest
uv lock --check
```

Add dependencies through `pyproject.toml` and regenerate the lockfile:

```shell
uv add <package>
uv add --dev <package>
uv lock
```

Do not edit `uv.lock` manually. Do not commit `.venv/`, caches, local
environment files, or generated package output.

## AWS project conventions

### Lambda code

Keep Lambda handlers under `lambdas/` and shared code under `commons/`.
Generate Lambda support files through the Syndicate command rather than
manually recreating the required configuration:

```shell
syndicate generate lambda \
    --name ExampleLambda \
    --runtime python \
    --project-path .
```

The generated Lambda configuration uses the current default Python runtime
(`python3.14`). Explicit runtime values in existing configurations must be
preserved unless a migration is intentional.

### Deployment resources

`deployment_resources.json` describes the resources used by the generated
project. Environment-specific Syndicate configuration belongs in the project
configuration files and must not contain committed credentials.

### Build and deployment

Build locally before requesting an AWS operation:

```shell
syndicate build
```

The following commands can mutate AWS resources and require explicit review of
the target account, region, and resource scope:

```shell
syndicate deploy
syndicate update
syndicate clean
```

Instructions in `AGENTS.md` guide contributors but are not a security boundary.
Use AWS IAM, CI permissions, approvals, and command-level safeguards for
enforcement.

## Testing and quality

Keep the quality pyramid explicit:

- `tests/unit/` contains deterministic tests with no network or AWS access.
- `tests/integration/` contains package and CLI boundary tests.
- `tests/e2e/` contains tests that may require deployed resources.

For every behavior change:

1. Add or update a focused unit test.
2. Run the focused test first.
3. Run the complete test suite.
4. Run lockfile and formatting checks that the project configures.
5. Review the final diff for secrets, generated output, and unrelated changes.

Smoke and end-to-end tests must not run accidentally from a unit-test command.
They require documented credentials, an approved AWS account, and an explicit
resource lifecycle plan.

## Instruction layering

Use one canonical project instruction file:

1. `AGENTS.md` contains provider-neutral repository rules.
2. `README.md` contains human setup and usage.
3. This document contains the detailed project-structure standard.
4. Tool-specific adapters, such as `CLAUDE.md`, may point to `AGENTS.md` but
   must not silently replace it.
5. A portable `skills/<name>/SKILL.md` may describe a repeatable workflow, but
   it must not become a second architecture or dependency authority.

No provider-specific file is required unless the project deliberately supports
that provider. In particular, do not add `SKILLS.md` merely because an
assistant exists.

## Maintenance

When the project structure changes, update these together:

- the generator implementation;
- the generated `AGENTS.md`, README, and architecture templates;
- this document;
- generator tests;
- the root README or changelog when the user-visible CLI changes.

The standard is successful when a new checkout can generate a project, resolve
its dependencies with `uv`, run its offline tests, and clearly separate local
quality checks from AWS-mutating operations.
